# 完整分析与建议

## 一、对业务链路的理解(口径确认)

整条链路是:队列(G1–G10,按类目划分)产出带违规码/规则码的 case → 自动驳回模型(策略因子 + 正则 + fewshot,召回 95%)拦截高置信违规 → 漏放的 5% 和低准确率部分进入人审 → AI 助审 Agent 在人审前运行,通过 product_id 调商品信息插件取标题/主图/详情图/SKU/资质,再经「获取规则」和「违规点引用整理」节点清洗规则、定位细则,把疑似违规点透传到 TCS 给审核员参考。

两个北极星指标是**单 case 人审时长下降**和**助审覆盖量**,当前瓶颈是助审信息精确率只有 ~11%,召回/准确率 ~50%,且评估集本身有标注偏差。

## 二、为什么精确率会卡在 11%——先做误差归因,再谈方案

11% 这个数字说明问题大概率不在「模型能力不够」,而在**链路误差叠加 + 评估口径失真**。建议先做一次分层归因,把每个环节的误差单独量化,否则后面 RAG 和检测模型的收益无法归因:

### 1. 评估集偏差先修

已知标注有偏,那么 11% 是「真实精确率」还是「评估精确率」都存疑。先抽 200–500 条,用研判/质检过的双人标注 + 仲裁重标,算出标注一致率(Kappa),得到一个可信的基线。如果修正后精确率明显高于 11%,优先级就要重新排。

### 2. 规则定位误差和违规点判断误差分开算

Agent 是「先定位到规则类目下的细则,再拿商品信息对比」。要分别统计:

- 细则定位对了但违规点说错的比例;
- 细则本身就定位错的比例。

如果规则清洗/引用节点错了,后面全错——这是典型的误差放大点。

### 3. 输入信息质量

商品插件取回的详情图 OCR、资质图是否可读、SKU 信息是否残缺,对多模态判断影响很大。统计一下「信息不全的 case」和「信息完整的 case」精确率差多少。

### 4. 样本分布问题

进入人审的本来就是自动驳回模型「不确定」的 5% 漏放 + 低准确率 case,这是一个被前置模型筛过的**难样本分布**。用全量分布的 fewshot 或规则去打难样本,精确率低是结构性的,不完全是 Agent 的错。这一点在向治理方汇报时值得明确讲清楚。

## 三、对高质量数据集 + RAG + 治理检测模型的建议

方向是对的,几个落地细节:

### 数据集构建

- 以质检/研判复核后的结论为 label,而不是一审结论;
- 每条 case 存结构化字段(队列、类目、违规码、细则 ID、命中的证据位置——标题片段/第几张图/资质字段),而不只是「违规/不违规」;
- **固证字段(evidence)是 RAG 检索后最有价值的部分**,因为它直接告诉模型「相似商品当时是哪个要素违的规」。

### RAG 检索键

不要只用商品标题做 embedding,建议用「类目 + 违规码 + 标题 + 主图特征」做多路召回,再重排。同违规码下的历史 case 比全局相似 case 参考价值高得多。

### 治理检测模型的定位

目标是「规避每次配多个自动驳回模型 + 放到 Agent 前部做检测」。建议把它定位成**统一的多标签风险分类器**(输出违规码概率 + 置信度),按置信度分层路由:

| 置信度 | 路由 |
| :--- | :--- |
| 高置信 | 直接走驳回 |
| 中置信 | 带着预测 Tag 进 Agent 做细则定位 |
| 低置信 | 直接透传人审 |

这样它同时替代了「多套驳回模型的配置成本」和「Agent 缺少先验」两个问题,而且置信度分层天然对接现有的灰度/全量/质检发布流程。

### 规则变更的运营闭环

治理规则由治理方制定且会变,细则 ID 要做版本化,否则历史 case 的 label 会随规则更新失效——这是这类数据集最常见的腐化原因。

## 四、助审产品指标上的一个提醒

精确率低时,透传给审核员的「违规点参考」可能反而增加阅读成本、甚至造成锚定效应(审核员倾向确认 AI 的说法)。建议:

- 在 TCS 侧埋点对比「有助审 vs 无助审」的单 case 时长和一审准确率;
- 给透传信息加置信度标识,低置信不展示或折叠展示;
- 覆盖量扩大应该跟着精确率走:先在某个「队列 × 体裁」组合(比如静态商品 × 某高频违规码)做到精确率 60%+ 再横向铺,比全面铺开但处处 11% 对指标更有利。
