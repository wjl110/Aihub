# 基于研判表的 RAG / 数据集 / SFT 设计方案

> 记录日期:2026-07-12 · 基于研判任务明细表(36 字段)的完整数据方案

## 〇、先说最重要的判断

这张研判表是一张**标签表,不是训练数据表**——它有结论(三级治理标签、是否治理问题、底线分类),但**没有内容**(没有标题、没有直播切片、没有图片,备注和送审备注大多为 NULL)。

所以整个方案的第一步不是建 RAG,而是**内容回捞**:以 `研判对象ID` / `问题对象ID` 为外键,按 `研判对象类型` 路由抓取内容。直播回放会过期,回捞管道必须按 `日期分区` 每日增量跑。

```
研判表(标签)──join──▶ 内容回捞(快照)──▶ 样本宽表 ──┬─▶ RAG 索引
                                                      ├─▶ 评估集
                                                      └─▶ SFT 训练集
```

## 一、字段逐个怎么用(36 字段用途映射)

| 字段 | 用途 |
| :--- | :--- |
| 日期分区 | 增量管道调度键;训练/测试**按时间切分**的依据 |
| 研判任务ID / 研判CASEID | 主键与去重(同一 case 可能多个任务,取最新完成的) |
| 研判对象类型 / 问题对象类型 | **体裁路由**:直播/商品/短视频走不同的内容回捞器 |
| 研判任务归属团队 | 域过滤(只取 CQC) |
| 信号来源 | 分层维度:人工导入 / 模型送审 / 举报的分布完全不同,评估要分开报 |
| 研判任务类型 / 场景ID / 场景名称 | **限定语义域**:不同场景(如「拉铃初审复核」)的标签口径不同,v1 建议锁定单一场景 |
| 研判任务状态 | 过滤条件:只取「已研判」 |
| 研判主体ID | **防泄漏切分键**:同一商家/达人的 case 不得跨训练/测试集 |
| 研判对象ID / 问题对象ID | **内容回捞外键**(注意:表头中「研判对象ID」出现了两次,先和数仓确认哪列是真的) |
| 研判CASE所属G行业 | 队列元数据,RAG 检索的过滤字段 |
| 违规切片开始/结束时间 | **直播体裁的证据锚点**:告诉你违规发生在哪一段,是回捞窗口也是弱监督信号(结束时间可能为 NULL,需兜底) |
| 研判任务创建/完成时间 | 时效分析;数据新鲜度监控 |
| 完成人ID/姓名/邮箱/部门 | **入库前脱敏**:训练集直接删;质量分析场景保留 hash 后的 ID 即可 |
| 研判case备注 / 送审备注 | 稀疏但珍贵的自由文本理由,非 NULL 的单独捞出来做 SFT 理由参考 |
| 是否治理问题 | **二分类 golden label**;「否」的就是负样本(千万别丢) |
| 治理标签分类:底线/非底线 | 风险等级 label,置信度分流策略的输入 |
| 治理一级/二级/三级标签 | **主标签体系**(层级分类的训练目标) |
| 规则是否覆盖 | 关键字段:=否 的 case 是**规则缺口**,单独存一份做规则挖掘,且**不能**用于训练自动驳回模型(现有规则体系解释不了它) |
| 主观/客观 / 客观标签 | 若填充率高,是「可自动化程度」的信号(客观题优先做替代);示例中为 NULL,先查全表填充率 |
| 审核标签-中文 | **第二标签体系**(审核视角的标签路径),与治理标签建映射表,两边不一致的 case 单独审 |
| 不处置原因 | 困难负样本的解释文本,SFT 负样本的输出理由直接可用 |

## 二、数据管道:从研判表到样本宽表

### 2.1 清洗规则

1. 过滤:`研判任务状态=已研判` + `归属团队=CQC` + 锁定目标场景;
2. 去重:按 `研判CASEID` 取 `研判任务完成时间` 最新一条;
3. 正负样本:`是否治理问题=是` → 正样本(label = 三级标签);`=否` → 负样本(理由 = 不处置原因);
4. 剔除或单独标记:`规则是否覆盖=否` 的入「规则缺口池」;
5. 脱敏:删除完成人姓名/邮箱/部门,保留 hash 后的完成人 ID;
6. 质量检查:统计每个字段的 NULL 率、三级标签的类目分布(长尾类合并到二级)、两套标签体系的映射一致率。

### 2.2 内容回捞(按体裁路由)

| 体裁 | 回捞内容 | 处理 |
| :--- | :--- | :--- |
| 直播 | `违规切片开始~结束时间` 的回放片段 | ASR 语音转写 + 按秒抽关键帧 + 关键帧 OCR;切片结束时间 NULL 时取开始后 N 分钟兜底 |
| 商品(静态) | 标题、主图、详情图、SKU、资质 | 详情图 OCR;全部存审核时刻快照 |
| 短视频 | 视频、封面、文案 | ASR + 关键帧 + OCR |

回捞结果与研判表 join 成**样本宽表**,一行 = 一个已终判 case 的「内容 + 标签 + 证据窗口」。

### 2.3 样本宽表结构(核心字段)

```
case_id, media_type, g_industry, scene_id,
subject_id(防泄漏用), object_id,
content: {title, asr_text, ocr_text, keyframe_urls, detail_images, sku, qualification},
slice_window: {start, end},
label: {is_violation, is_bottomline, l1, l2, l3, audit_label_path},
rule_covered, no_action_reason, remark,
partition_date, dataset_version
```

## 三、RAG 设计

### 3.1 检索单元:case 卡片

一条索引记录 = 一个历史已终判 case,payload 包含:

```json
{
  "case_id": "...",
  "label_path": "虚假宣传 > 服务履约虚假-达人 > 售后服务不符-达人",
  "is_bottomline": true,
  "content_summary": "直播切片 ASR 摘要 / 商品标题+详情要点(LLM 预生成,200 字内)",
  "evidence_desc": "主播在 12:27-12:30 口播承诺'七天无理由退货不扣邮费',实际店铺售后政策不符",
  "metadata": {"media_type": "直播", "g_industry": "G3", "scene_id": 20453}
}
```

### 3.2 多路召回 + 重排

1. **结构化过滤(必须先做)**:`media_type` + `g_industry` + 一级/二级标签(如果入参已带违规码,映射到一级标签过滤)——同标签域内的历史 case 参考价值远高于全局相似;
2. **文本稠密检索**:标题 + ASR/OCR 摘要做 embedding(中文用 bge 系列),查询侧用新 case 的同构内容;
3. **图像检索(可选二期)**:关键帧/主图用 CLIP 类模型;
4. **重排**:召回 top-50 → 交叉编码器(bge-reranker)排到 top-5;
5. 输出给 Agent 的格式:每条含「标签路径 + 证据描述 + 相似点」,作为动态 few-shot 注入违规判断节点。

### 3.3 存储

向量库(Milvus / ES 混合检索均可)存 embedding + metadata;宽表原始内容留在数仓,payload 只放摘要,命中后按需回源取全文/图。

### 3.4 更新与淘汰

- 每日增量:新终判 case 进索引;
- 规则版本变更:受影响标签下的历史 case 打「待复核」标,复核前降权;
- 同款商品/同主播重复违规的 case 去重,防止检索结果被单一主体刷屏。

## 四、数据集(评估集优先于训练集)

### 4.1 任务定义(建议拆三个)

| 任务 | 输入 | 输出 | 用途 |
| :--- | :--- | :--- | :--- |
| T1 违规判别 | 内容快照 | 是否治理问题(二分类) | 检测模型/自动驳回 |
| T2 层级标签分类 | 内容快照 | L1/L2/L3 标签 | 替代人工选标签 |
| T3 证据定位与理由 | 内容快照 + 标签 | 切片时间/文本片段 + 理由 | 助审透传、复核证据 |

### 4.2 切分原则

- **按时间切分**:测试集用最近的日期分区(如最后一个月),模拟真实上线;
- **按主体隔离**:同一 `研判主体ID` 不跨集(同一商家的违规话术高度雷同,随机切分指标必然虚高);
- 分层抽样:按 `体裁 × G行业 × 一级标签 × 信号来源` 分层,报指标时也按层报;
- 长尾处理:三级标签样本 <50 的类,评估归并到二级,训练时单独观察。

### 4.3 规模参考

- 评估集:每个体裁 × 高频一级标签至少 200 条(含正负),先把评估集建可信,再谈训练;
- 负样本占比不低于 50%,且要包含「送审了但研判为不处置」的困难负样本(这批天然存在于 `是否治理问题=否`)。

## 五、SFT 设计

### 5.1 样本格式(输出必须是结构化 JSON)

```json
{
  "instruction": "你是电商内容治理审核专家。根据以下直播切片内容和候选规则,判断是否存在治理问题,给出标签路径、证据和理由。",
  "input": {
    "media_type": "直播",
    "g_industry": "G3",
    "content": {
      "asr_text": "主播口播转写……",
      "ocr_text": "画面挂载商品信息……",
      "keyframes": "[图片或图片描述]"
    },
    "candidate_rules": "按一级标签检索到的 3-5 条细则原文"
  },
  "output": {
    "is_violation": true,
    "is_bottomline": true,
    "label_path": ["虚假宣传", "服务履约虚假-达人", "售后服务不符-达人"],
    "evidence": [{"type": "asr", "time_range": ["12:27:23", "12:28:10"], "quote": "……"}],
    "reason": "主播承诺的售后权益与店铺实际政策不符,违反细则X.X"
  }
}
```

负样本的 output:`is_violation=false` + `reason` 直接用 `不处置原因` 字段改写。

### 5.2 理由(CoT)从哪来:拒绝采样蒸馏

研判表只有标签没有推理过程,标准做法:

1. 拿强模型(线上最好的 LLM),给它内容 + **golden 标签** + 规则原文,让它生成「为什么是这个标签」的推理和证据定位;
2. **一致性过滤**:再让模型不看标签只看内容做一遍判断,两次标签一致的样本才保留(拒绝采样);
3. 人工抽检 5–10% 生成理由的质量,合格后作为 SFT 的 output;
4. 这样蒸馏出的数据同时服务 T2(标签)和 T3(证据+理由)。

### 5.3 训练要点

- 底座:选已有多模态能力的底座(关键帧要看图),没有条件就先纯文本(ASR+OCR)起步;
- 方法:LoRA 起步(数据量万级以内全参容易过拟合);
- 类别均衡:头部标签每类设上限(cap),防止模型学成「多数类分类器」;
- 输出格式训练:JSON schema 严格约束,格式错误率是上线前必查指标;
- 评估:L1/L2/L3 分级准确率 + macro-F1(长尾敏感)+ 证据命中率(预测切片与研判切片的 IoU / 文本重合度),都在按时间切分的测试集上报。

### 5.4 和现有链路的关系

- SFT 后的模型 = 之前规划的「统一治理检测模型」的实现路径;
- RAG 和 SFT 不互斥:推理时检索 top-5 相似终判 case 注入上下文,可以显著缓解长尾标签的样本不足;
- 上线走现有灰度 → 全量 → 质检流程,先在评估集对齐置信度校准,再定分流阈值。

## 六、这张表暴露的数据质量问题(先确认再动工)

1. **「研判对象ID」在表头出现两次**——先和数仓确认哪一列是真实外键;
2. `主观/客观`、`客观标签`、`备注` 大量 NULL——统计全表填充率,填充率 <20% 的字段不要设计依赖;
3. **两套标签体系并存**(治理三级标签 vs 审核标签路径)——必须先建映射表,映射冲突的 case 单独复核,这直接影响 label 质量;
4. `违规切片结束时间` 为 NULL——直播回捞窗口需要兜底规则;
5. 表里有完成人姓名/邮箱/部门——任何出库/训练前先脱敏,这是合规红线;
6. 单一场景(拉铃初审复核)的标签口径不一定等于其他场景——v1 锁定单场景,扩场景时重新校验标签一致性。

## 七、执行顺序(可直接排期)

1. 和数仓确认重复列、字段填充率、可回捞的内容源与保存时效;
2. 搭内容回捞增量管道(直播切片优先,时效最紧);
3. 建样本宽表 + 两套标签映射表;
4. 先建**评估集**(分层抽样 + 时间切分),跑通 L1/L2/L3 指标基线;
5. RAG 索引上线,先给现有 Agent 注入相似 case,量化增益;
6. 拒绝采样蒸馏生成 SFT 数据 → LoRA 训练 → 评估集对比 RAG-only / SFT-only / SFT+RAG;
7. 置信度校准 → 按队列灰度上线。
