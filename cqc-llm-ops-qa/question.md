# 问题原文

> 记录日期:2026-07-12

在字节 CQC 做大模型运营,主要工作是根据电商商家的违规商品和其业务治理需求,进行搭建自动驳回模型(由策略因子、正则表达式、fewshot 等)经过事前、事中、事后以及灰度、全量、质检等程序进行发布线上,还要和提需求方:电商治理沟通,且治理规则大部分由治理制定。

其次是 AI 助审项目,这块主要是利用 Agent 的线上人工审核的数据运行结果透传到 TCS 平台(人审平台)给人工审核做一个信息参考,参考目前的违规点有哪些等等,最终是要减少人审时过每个 Case 的时间,其次是扩大这个助手的覆盖量。

对于电商治理来说,有假货商品、虚假宣传、劣质等;对于体裁来说有静态商品、直播、短视频;队列来说有很多,比如 G1–G10,每个队列有一些类目,比如母婴类、护理类、箱包类等等。

工程提供了一些参数,我们可以将这些参数比如 product_id 入参,利用一个获取商品信息的插件提取出其他所有信息,比如商品详情、SKU 图、SKU 信息等等,然后里面有个获取规则的节点。入参环节其实还有很多违规码、规则码等等,这些参数是队列出来后获取到的。

就是说这些参数在每条队列中首先经过自动驳回模型之后,模型有 95% 的召回率,满足则驳回,有 5% 漏放,漏放的 case 走人审,准确率低的走人审。那此时的 case 就带有一些基本信息,里面也包含了违规点和违规码等等。

所以 Agent 在实际运行时还有违规点引用、整理的节点,会清洗规则,这用于参考商品属于具体违规类目下的哪条细则,会通过商品的标题、主图、详情图、资质等信息综合对比规则判断。(就是说商品属于这个规则类目下,他需要去遵循这个规则类目下的规则,但具体不知道是商品的什么违反了这条,所以要这样设计。)

所以最终最重要的就是提高 Agent 的信息准确率。目前精确率很低,大概在 11% 左右,受到多个误差和信息的干扰,召回率和准确率一般在 50% 左右,然后评估的数据集也有标注误差,属于有偏。

最后目前在做的就是准备找研判和质检后的高精准数据集,构建一波高质量数据集用来 RAG,训练一个治理检测模型,规避每次会配多个自动驳回模型,以及放到 Agent 前部分做检测。通过这些收集的高质量历史 case,包含文、图等信息,去预测相似 case 的原因和固证等,然后推荐出他的 Tag 等。
