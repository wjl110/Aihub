# 从「信息透传」到「结果复核」:TCS 界面降噪方案与数据集建设指南

> 记录日期:2026-07-12 · 针对「TCS 界面信息过载、助审反而拉长审核时长」的 GAP,以及首次建设数据集的新人指南

## 一、观察到的问题

TCS 审核界面上信息非常多且杂乱:视频标题、商家信息、违规点、可能涉及的品牌等等全部塞在一个页面上。审核员看这些信息已经很吃力,还要再看 AI 助手透传的信息——而透传信息本身精确率不高,审核员还得先判断「AI 说的对不对」。结果是:**平均处理时长不但没降,反而升高了**。明明是来提供帮助的,却提高了审核成本,这是最难受的点。

## 二、提出的方案

审核员真正要做的,不应该是「从一堆原始信息里自己找违规点」,而应该是**对机器已经判完的标签/结果做人工复核**:

- TCS 界面做减法:降低信息密度,做一个干净的界面;
- 信息分级折叠:需要的时候点开,不需要的时候不呈现;
- 默认呈现的只有一样东西:**机器已经判断好的结论,人工确认一遍即可**。

## 三、方案评价:方向对,但有一个硬前提和一个隐藏风险

### 3.1 方向是对的

这个方案本质上是把人的角色从「审核员(从原始信息中发现问题)」变成「复核员(验证机器结论)」,认知负荷完全不同:前者是开放式搜索任务,后者是封闭式验证任务,后者天然更快。这也和之前广告部门「替代优先」路线的观察一致——你等于是从助审路线推导出了替代路线的必要性,两条线合流了。

「信息分级 + 默认折叠 + 按需展开」在交互设计上叫**渐进披露(Progressive Disclosure)**,是处理高密度专业界面的标准做法,这部分无论精确率高低都值得做,属于无风险收益。

### 3.2 硬前提:机器结论的精确率必须先达标

复核模式成立的前提是**机器结论大部分时候是对的**。如果拿当前 ~11% 精确率的结论做默认展示,审核员每 10 条要推翻 9 条,复核比自己审还慢,而且会迅速失去对系统的信任(之后即使模型变好了,他们也不看了)。所以正确的打开方式是**按置信度分流,而不是全量切换**:

| 置信段 | 界面形态 | 人的角色 |
| :--- | :--- | :--- |
| 高置信(试点期建议精确率 ≥ 85% 的分段) | 只展示机器结论 + 一键证据展开 | 复核员:确认 / 推翻 / 改标签 |
| 中置信 | 展示违规点候选 + 证据锚点,不给结论 | 审核员:参考线索自行判断 |
| 低置信 | 干净的原始信息界面,不透传 AI 信息 | 审核员:传统审核,避免被低质信息干扰 |

### 3.3 隐藏风险:自动化偏见(Automation Bias)

复核模式下人会越来越倾向无脑点「确认」,错误会静默通过。必须配套三个机制:

1. **金标暗桩(gold case / trap case)**:在复核队列里随机混入已知答案的 case(包括故意做错的机器结论),监控每个复核员的「抓错率」;
2. **盲测对照组**:保留一小部分流量不展示机器结论,对比两组的一审准确率,持续量化「锚定效应」的大小;
3. **质检兜底**:复核通过的 case 保持抽检比例,复核一致率异常(比如确认率长期 >98%)时告警。

## 四、落地路径(四个阶段)

### 阶段 0:量化现状(先拿数据,再动界面)

- 和工程沟通在 TCS 埋点:每个信息模块的展开/点击/停留数据,AI 助手信息的采纳率(审核结论与透传违规点一致的比例);
- 访谈 5–10 名审核员:审一条 case 的实际动线是什么,先看什么后看什么,哪些信息从来不看;
- 产出:信息模块使用率排行 + 当前 AHT(平均处理时长)基线,按队列拆分。

### 阶段 1:界面降噪(不改变判断责任)

- 信息分三级:**默认展示**(判断必需)/ **一键展开**(偶尔需要)/ **深度折叠**(极少需要);
- 证据锚定:违规点不要用一段文字描述,直接高亮到载体上——标题片段标红、图片上画框(bounding box)、资质字段定位,点违规点跳转到对应位置;
- 给 AI 透传信息加置信度标识,低置信不展示。

### 阶段 2:高置信队列试点复核模式

- 选一个标签收敛、规则明确的队列(高频违规码 × 静态商品是最佳起点);
- 界面改为:机器结论卡片(违规码 + 命中细则 + 证据缩略)+ 三键操作(确认 / 推翻 / 改标签);
- 同步上线金标暗桩和盲测对照组。

### 阶段 3:度量与扩量

- 北极星:试点队列 AHT 下降幅度、复核准确率(以质检结论为准);
- 扩量条件:某队列的机器结论精确率达标即切入复核模式,精确率跟不上的队列停留在阶段 1 的降噪界面;
- 每次扩量都走灰度 → 全量 → 质检的现有发布流程。

## 五、涉及的技术方案

| 环节 | 技术 | 说明 |
| :--- | :--- | :--- |
| Agent 输出 | 结构化 JSON Schema | 违规码、细则 ID、置信度、证据锚点数组,禁止自由文本堆砌;这是前端能做分级折叠的前提 |
| 文本证据锚定 | 字符区间(span offsets) | 记录违规文本在标题/详情中的起止位置,前端据此高亮 |
| 图片证据锚定 | OCR + 目标检测框(bbox) | 记录违规区域在第几张图的什么位置,前端画框 |
| 置信度校准 | Temperature Scaling / Isotonic Regression | 模型原始分数 ≠ 真实概率,必须在验证集上校准后才能用于分流阈值 |
| 相似 case 检索(RAG) | 向量库(Milvus / Faiss / ES 混合检索) | 多路召回:违规码倒排 + 文本 embedding + 图片 embedding,再重排 |
| 数据存储 | 数仓明细表(Hive/ClickHouse)+ 向量索引 | 明细表存全字段用于训练评估,向量索引只存检索需要的 |
| 界面 | TCS 平台定制组件 | 需要和 TCS 平台方/工程约定结构化 payload 的接口契约 |

## 六、数据库/数据集字段结构定义

按五张逻辑表设计(实际可以是数仓里的五张表或一张宽表 + 维表),核心原则:**机器判断、人工复核、质检终判必须分开存,不能互相覆盖**。

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| case_id | string | 主键,一次审核事件 |
| product_id | string | 商品 ID |
| queue_id | string | 队列(G1–G10) |
| category_path | string | 类目路径,如 母婴/奶粉/婴儿配方 |

| source | enum | 来源:自动驳回漏放 / 低准确率分流 |
| created_at | timestamp | 进入队列时间 |

### 6.2 商品快照表(item_snapshot)

商品信息会变,**必须存审核时刻的快照**,不能只存 product_id 事后再查:

| 字段 | 类型 | 说明 |

| ocr_text | json | 各图 OCR 结果(离线预计算,训练和检索都要用) |

### 6.3 机器判断表(machine_judgment)

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| case_id | string | 关联主表 |
| model_version | string | 模型/Agent 版本(必须存,否则无法归因) |
| predicted_code | string | 预测违规码 |
| predicted_rule_id | string | 预测命中细则 |
| confidence | float | 校准后置信度 |
| evidence | array<json> | 证据锚点数组,见下 |
| agent_trace_id | string | Agent 运行轨迹 ID,用于回溯中间节点 |

evidence 元素结构:

```json
{
  "source": "title | main_image | detail_image | sku | qualification",
  "modality": "text | image",
  "locator": {"span": [12, 18]} ,
  "content": "命中的原文片段或图片区域描述",
  "reason": "违反细则 X.X:...(引用规则原文)"
}
```

图片证据的 locator 为 `{"image_index": 2, "bbox": [x, y, w, h]}`。

## 七、数据集标准如何建立(新人版流程)

### 7.1 建立顺序

1. **写标注规范 v0**:给每个违规码写清楚定义 + 3 个典型正例 + 3 个典型负例 + 2 个边界 case 及其判法。没有这个文档,后面所有标注都是各标各的;
2. **小规模试标**:抽 100–200 条,两人独立标注,算一致率(Cohen's Kappa)。Kappa < 0.6 说明规范有歧义,回去改文档,而不是继续标;
3. **正式标注**:双人标注 + 不一致仲裁(由研判/资深质检出终判),目标 Kappa ≥ 0.75;
4. **数据划分**:训练/验证/测试**按时间切分**(比如测试集用最近一个月),并保证同一 product_id 不跨集合出现——否则指标虚高;
5. **版本化**:数据集打版本号,并绑定规则版本号;规则改版时,受影响违规码的历史 label 标记为待重审。

### 7.2 数据集必须包含什么

- **负样本(合规商品)**:比例建议不低于正样本,而且要包含「长得像违规但其实合规」的困难负样本(这是精确率的关键);
- **各队列 × 体裁 × 违规码的分层覆盖**:按线上分布分层抽样,不要只收好标的;
- **证据锚点**:每条违规样本必须标到「是哪个字段/哪张图的哪个位置违规」,只有 case 级 label 训不出可解释的模型;
- **难例集单独维护**:被自动驳回模型漏放的、人机不一致的、质检推翻一审的,单独打难例标记,评估时单独报指标。

### 7.3 指标口径先统一

新人最容易踩的坑是口径混乱,先和治理方书面约定:

- 精确率/召回率按什么粒度算:**case 级**(这条该不该驳回)还是**违规点级**(指出的每个违规点对不对)?两者数字差异巨大,你们目前的 11% 大概率是违规点级;
- 以谁为真值:一审结论(噪声大)还是质检/研判终判(推荐);
- 置信度分流阈值在哪个数据集上定:必须是校准后、时间上晚于训练数据的验证集。

## 八、新人避坑清单(汇总)

1. **只收违规样本,不收合规样本** → 模型学不会「什么是正常」,精确率永远上不去;
2. **拿一审结论当 label** → 一审本身有错误率,等于用带噪声的答案教模型;用质检/研判终判;
3. **不存快照** → 商品信息改了之后,历史数据无法复现,整条样本作废;
4. **不存规则版本和模型版本** → 规则改版后分不清「模型错了」还是「标准变了」;
5. **训练/测试随机切分** → 同商品、同商家、同时间段泄漏,线下指标好看、线上不行;
6. **不做置信度校准就定分流阈值** → 模型分数 0.9 不等于 90% 正确,阈值形同虚设;
7. **界面改版不留对照组** → AHT 变化无法归因是界面的功劳还是模型的功劳;
8. **复核模式不设金标暗桩** → 自动化偏见静默积累,出事才发现;
9. **一次性全队列铺开** → 不同队列精确率差异巨大,统一切换必然翻车,按队列灰度;
10. **忽略脱敏合规** → 商家信息、审核员 ID 入库前先脱敏,数据集外发一定走合规审批。

## 九、埋点具体怎么做(追问补充)

> 追问:埋点怎么埋?信息只是透传,人可能点「采纳/不采纳」按钮,是埋在按钮上吗?CoT 透传的信息是「看」的,不一定会手点,这怎么测?

### 9.1 按钮要埋,但它是最不重要的信号

「采纳/不采纳」按钮当然埋(事件带 case_id、审核员、AI 结论与模型版本),但显式反馈率通常很低且有敷衍成分。**真正可靠的采纳率不需要按钮**——后端本来就有审核员最终提交的结论,直接和 AI 透传的违规码对比:

- **结论一致率** = 最终提交违规码 == AI 预测违规码(纯后端 join,零前端改造);
- **疑似真实采纳** = AI 已曝光 + 结论一致 + 处理时长低于该审核员基线,三个条件同时满足才算,排除巧合撞对。

### 9.2 「看了但不点」的测量手段(按信号强度排)

| 信号 | 埋法 | 强度 |
| :--- | :--- | :--- |
| 曝光(impression) | IntersectionObserver 监听 AI 卡片进入可视区域,记录曝光起止得到曝光时长;区分「渲染了」和「滚到看见了」 | 弱 |
| 展开/折叠 | CoT 默认折叠,点「查看推理过程」才展开,展开即明确阅读意图 | 强 |
| 复制文本 | 监听 copy 事件(复制违规点去搜索/填单是强使用信号) | 强 |
| 停留时长分解 | 打开 case → 首次交互 → 提交分段计时;AI 卡片曝光时长占单 case 总时长比例 | 中 |
| hover 悬停 | 鼠标在 AI 区域停留时长 | 弱,可选 |

关键设计技巧:**默认折叠不只是降噪,更是把「看」从被动行为变成主动点击,让阅读变得可测量**。这和界面降噪是同一个动作的两面。

### 9.3 CoT 透传的三层设计

CoT 原文冗长,直接透传就是「信息更多更烦」的来源。做成三层:

1. **一级(默认展示)**:一句话结论——违规码 + 命中细则 + 置信度标识;
2. **二级(一键展开)**:结构化证据——标题第 X 段 / 第 N 张图什么位置违反细则第几条,高亮锚定到原文/原图;
3. **三级(再点一层)**:CoT 推理全文,给想深究的人。

每层的展开率就是天然的价值度量:三级展开率长期 <5%,说明 CoT 全文没人需要,链路上可以停掉。

### 9.4 埋点事件表结构(参考)

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| event_id | string | 主键 |
| case_id | string | 关联 case 主表 |
| reviewer_id | string | 审核员(脱敏) |
| ui_mode | enum | 复核模式 / 降噪模式 / 传统模式 |
| event_type | enum | impression_start / impression_end / expand / collapse / adopt_click / reject_click / copy / submit |
| target_module | enum | ai_conclusion / ai_evidence / ai_cot / rule_ref / item_info / … |

| extra | json | 展开层级、AI payload 版本等 |

### 9.5 比埋点更重要的:实验设计

只有埋点得到的是相关性(「看了 AI 信息的 case 审得慢」可能只是难 case 才需要看)。归因必须有对照:

- **空白对照**:随机 5–10% 的 case 不展示 AI 信息,对比 AHT 与一审准确率——这是「AI 助手有没有帮助」的唯一干净答案;
- **先判后示**(小流量):审核员先给初判,再展示 AI 信息并允许改判;初判与 AI 的一致率测真实增益,改判方向和比例测锚定效应强度;
- 优先用**同一审核员**在两种模式下的数据对比(within-subject),排除个体熟练度差异。

## 十、第一步做什么(可直接执行)

1. 从质检/研判库里拉 200 条已终判的 case,亲手按第六节的字段结构整理成表格(哪怕先用表格软件),你会立刻发现哪些字段拿不到、哪些定义有歧义——这就是和工程、治理对齐的需求清单;
2. 挑 1 个高频违规码写标注规范 v0(定义 + 正负例 + 边界 case);
3. 和另一个同事各自独立标 50 条,算一致率,体会「规范歧义」长什么样;
4. 拿这 200 条按第 6.3 节的 evidence 结构人工标出证据锚点,这份小数据就是你第一版 RAG 库和检测模型评估集的种子。
